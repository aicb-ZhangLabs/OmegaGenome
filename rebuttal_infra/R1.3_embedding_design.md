# R1.3 — pretrained-embedding-as-input: parameter sizes & layer logic

Reviewer R1.3: *"In the baseline one-hot encoding is used … wouldn't it be more reasonable to use a sequence
embedding from a model trained on a large amount of unlabeled data?"*

We replace the BPNet student's **one-hot input** with **per-base-pair embeddings** from a pretrained DNA model
(NT-2.5B or DNABERT-2), via a tiny input adapter. Everything downstream of the input is unchanged, so any
accuracy difference is attributable to the input representation, not capacity.

## 1. Parameter sizes (DEPLOYMENT student)

The deployable student = `backbone (dilated conv stack) + classifier head + input_adapter`.

| Student input | backbone | classifier | input adapter | **deployable total** | Δ vs one-hot |
|---|--:|--:|--:|--:|--:|
| **one-hot** (baseline) | 120,964 | 130 | 0 | **121,094** | — |
| **NT-2.5B embedding** | 120,964 | 130 | **10,244** | **131,338** | **+10,244 (+8.5%)** |
| **DNABERT-2 embedding** | 120,964 | 130 | **3,076** | **124,170** | **+3,076 (+2.5%)** |

- The **input adapter is a single 1×1 convolution** mapping `embedding_dim → 4` channels:
  NT-2.5B `2560→4` = 2560·4 + 4 = **10,244**; DNABERT-2 `768→4` = 768·4 + 4 = **3,076**.
  It is the ONLY added parameter; the dilated-conv backbone (which expects a 4-channel one-hot-like input)
  and the classifier head are byte-identical to the one-hot student.
- So the pretrained-embedding student is still a **~0.12 M sub-million-scale deployable model** — the adapter
  adds <9% (NT) / <3% (DNABERT-2). The paper's deployment claim is unaffected.

### Training-only parameter (not deployed)
When the feature-alignment KD term is on (`weight_mse > 0`), the student additionally carries a **teacher
projection** (student features → teacher's 2560-dim, for the MSE loss), ≈ **164 k** params. This is a
**training-time-only** module — it is discarded at inference and is NOT part of the deployable student
(the model-construction log prints "with teacher proj" vs "deployment parameters"). The results CSV's
`student_total_params` includes it during training; the deployable size is the table above.

## 2. Adapter logic

`distill_nt_embedding.py` builds `BPNetClassifierConfig(input_mode=nt_embedding, embedding_dim=<source dim>)`.
- `input_mode=onehot` → no adapter, raw 4-ch one-hot (untouched baseline).
- `input_mode=nt_embedding` → a 1×1 conv `input_adapter` projects the per-bp embedding (`embedding_dim` ch)
  down to the 4 channels the backbone expects. KD targets always come from NT-2.5B (apples-to-apples);
  only the *input representation* swaps.

## 3. Layer logic (which hidden layer the embedding comes from)

A transformer exposes `n_hidden_states = 1 (token-embedding) + n_transformer_layers`:
- **NT-2.5B**: 33 hidden states → index 0 = token embedding, indices 1–32 = transformer layers.
- **DNABERT-2**: 13 hidden states → index 0 = token embedding, indices 1–12 = transformer layers.

`embedding_layer` is configurable (`--embedding-layer`), folded into the cache key so layers don't collide:
- **default = MIDDLE layer** `n_hidden_states // 2` (NT idx 16, DNABERT-2 idx 6).
- `-1` = last layer; `k` = exact index.

**Why middle (not last):** the **last** layer of a *task-fine-tuned* model is the most task-specialized
(tuned toward that task's classifier) — the least general choice for a "pretrained sequence embedding," and it
risks leaking the teacher's task signal. **Middle** layers carry the most transferable, context-rich sequence
representations (standard representation-probing finding), so they are the principled choice for R1.3.

## 4. Would just the token-embedding layer (index 0) be enough?

Short answer: **probably not as the primary, but it is a valuable control.**
- Index 0 is the raw **learned per-token (k-mer) embedding lookup** — it carries only *token identity*, with
  **no sequence context** (no transformer processing). For DNA this is barely richer than one-hot: a conv
  student can already learn k-mer features from one-hot, so index-0 embeddings are expected to give ≈ no gain.
- The value of a pretrained transformer embedding is the **contextual** representation built by the
  transformer layers (middle/late layers integrate flanking sequence). That is where any improvement over
  one-hot must come from.
- **Recommended use:** keep the **middle layer** as the primary R1.3 result, and optionally run **index 0 as an
  ablation/control**. If index-0 ≈ one-hot while middle-layer > one-hot, that cleanly attributes the benefit to
  *learned context* (the transformer), not merely a richer input table — a clean, publishable ablation.
